# AI 에이전트 규칙

AI 코딩 에이전트(Claude Code, Codex CLI 등)는 쓸 수 있지만, 그 에이전트에 **에이전트 규칙을 반드시 넣어야 합니다**(전문은 이 페이지 맨 아래).
규칙은 다른 사람과 함께 쓰는 자원(네트워크, 스케줄러, GPU, 공유 스토리지)에 영향을 주는 행동에만 적용되고,
그 밖에 AI 도구를 쓰는 방식은 사용자가 정합니다. 자동 승인 모드에서도 규칙은 그대로 적용되고,
에이전트가 한 일의 책임은 그 에이전트를 실행한 사용자에게 있습니다.

## 규칙이 필요한 이유

에이전트는 사람보다 훨씬 빠르게, 지치지 않고 명령을 반복합니다. 실제로 AI 도구가 SSH 접속을 끝없이 재시도하다가
**기관 네트워크에서 클러스터 전체의 IP가 차단된** 사고가 있었습니다. 에이전트가 잡을 마구 내면 빈 GPU가 여러 노드에
조금씩 흩어져, 큰 잡이 들어갈 노드가 없어지기도 합니다(**GPU 자원 파편화**).

## 규칙 넣기

- **클러스터 노드**에서 실행하는 Claude Code와 Codex CLI에는 클러스터가 이 규칙을 자동으로 넣어 둡니다.
- **내 PC나 그 밖의 곳**에서 실행하는 에이전트에는 규칙 파일(사이트 주소 뒤에 `agents/AGENTS.md`)을 받아
  지침 파일이나 메모리로 넣어 주세요. Claude Code는 `CLAUDE.md`, Codex CLI는 `AGENTS.md`를 읽습니다.
  아래 [규칙 전문](#규칙-전문)도 같은 내용이지만, 링크가 전체 주소로 들어간 그 파일을 넣는 것이 좋습니다.

## 규칙별 이유

- **접속과 전송**: 위의 IP 차단 사고 때문입니다. 인증 실패가 쌓여도 접속한 IP가 차단됩니다.
- **잡 제출**: GPU를 필요한 만큼만 요청해야 빈 GPU가 한 노드에 모여 남아, 다른 사람의 큰 잡이 들어갈 수 있습니다.
  잡 제출 규칙 하나하나의 이유는 [클러스터 사용 규정](rules.md#잡-제출-규칙)에 있습니다.
- **요청을 몰아서 보내지 않기**: 스케줄러 조회를 빠르게 반복하면 스케줄러와 네트워크가 느려져 모든 사람이 영향을 받습니다.
  클러스터 명령의 `--json` 출력은 형식이 정해져 있어, 화면 출력을 잘못 읽고 같은 명령을 되풀이하는 일을 막습니다.
- **장시간 세션**: 남겨 둔 프로세스와 잡은 다른 사람이 쓸 CPU, 메모리, GPU를 계속 붙잡습니다.
- **로그인 노드와 공유 스토리지**: 한 사람의 I/O가 모든 사람의 잡을 느리게 합니다. 공간마다의 속도는
  [스토리지와 데이터](../guide/storage.md#공유-스토리지를-느리게-만들지-않는-법)에 있습니다.

````markdown
# AI 에이전트 규칙

이 규칙은 **다른 사람과 함께 쓰는 자원(네트워크, 스케줄러, GPU, 공유 스토리지)에 영향을 주는 행동**에만 적용된다.
그 밖에 AI 도구를 쓰는 방식(어떤 도구와 모드를 쓸지, 내 파일과 내 잡을 어떻게 다룰지)은 사용자가 정한다.
자동 승인 모드에서도 이 규칙은 그대로 적용된다.

## 접속과 전송

- 원격 접속(SSH, `scp`, `rsync`)이 실패하면 같은 서버에 **30초 이상** 간격으로 **최대 2번** 다시 시도한다.
  첫 시도를 포함해 세 번 연달아 실패하면 그 서버에는 더 접속하지 않고 **사용자에게 보고**한다.
    - 실패 횟수는 **서버마다 따로** 센다. 한 서버의 횟수는 **그 서버에** 접속이 성공했을 때만 처음부터 다시 센다.
      다른 서버에 접속이 성공해도 그 횟수는 그대로다. 접속이 잘 되는 동안의 접속 횟수를 제한하는 규칙이 아니다.
    - 예: 서버 A에 두 번 실패하고 세 번째에 성공하면 A의 횟수는 처음부터 다시 센다. 그사이 서버 B에 세 번 연달아
      실패했다면, A 접속이 잘 되더라도 B에는 더 시도하지 않고 보고한다.
    - 인증 실패(`Permission denied`, 틀린 비밀번호나 키)는 다시 시도하지 않고 바로 보고한다. 인증 실패가 쌓이면
      접속한 IP가 차단된다.
    - 자동 재시도 루프를 만들지 않는다.
- 접속이 잘 되더라도 짧은 시간에 새 접속을 여러 번 열지 않는다. 여러 명령은 한 번의 접속에서 실행하고
  (`ssh 서버 'cmd1 && cmd2'`), 같은 서버에 자주 접속하면 연결을 다시 쓴다([접속하기](../start/connect.md)의
  `~/.ssh/config` 예시처럼 `ControlMaster`를 켠다).
- 전송(`scp`, `rsync` 등)은 서버가 달라도 동시에 여러 개 띄우지 않는다. 앞의 전송이 끝난 뒤 다음 전송을 시작한다.

이유: 끝없는 접속 재시도로 기관 네트워크에서 클러스터 전체의 IP가 차단된 사고가 실제로 있었다.

## 잡 제출

- 잡을 내기 전에 **`sq`로 현재 자원 현황을 확인**한다. 잡 여러 개나 배열 잡을 한꺼번에 낼 때는 그 전에 한 번만 확인한다.
- GPU는 **필요한 만큼만** 요청하고, 그 수는 아래 [잡 제출 규칙](rules.md#잡-제출-규칙)의 노드당 GPU 수에 맞춘다.
  예: GPU 1장으로 실행되는 실험이면 1장만 요청한다.
- 비슷한 잡이 여러 개면 하나씩 반복 제출하지 않고 **배열 잡과 동시 실행 상한**을 쓴다(`--array=0-99%4`).
- GPU를 점유하는 세션(정의는 아래 "GPU를 점유하는 세션의 규칙")을 열어 둔 채 사용자의 다음 지시를 기다리지 않는다.
  사용자에게 묻기 전에 그 세션을 반납한다.

모든 사용자에게 적용되는 잡 제출 규칙(에이전트도 그대로 지킨다):

- **팀 QoS는 본인 소속 팀 것**을 쓴다. 본인 것은 `qos`로 확인한다.
- **GPU를 요청할 때는 GPU 타입을 명시**한다: `--gres=gpu:<GPU 타입>:4`처럼. 타입 이름은 `sq` 또는 `sinfo -o "%G"`로 확인한다.
- **GPU 잡은 파티션, CPU 수, 메모리를 지정하지 않는다.** 파티션은 GPU 타입으로, CPU와 메모리는 GPU 수에 비례해 **자동으로 정해진다**.

    파티션과 CPU 수는 적더라도 무시되고, 메모리를 적으면 제출이 거부된다. 처리 규칙 전체는
    [Slurm 레퍼런스: 자동 할당과 라우팅](../reference/slurm.md#자동-할당과-라우팅)에 있다.

- **노드당 GPU 수는 1, 2, 4, 8 중에서** 요청한다.
  여러 노드에 걸친 잡은 노드마다 같은 수를 받는다.
    - `--gpus=N`처럼 노드 수 없이 총 개수만 적으면 N 자체가 1, 2, 4, 8 중 하나여야 한다.
    - `-N`(노드 수)과 함께 적으면 총 개수 N을 노드 수로 나눈 값이 1, 2, 4, 8 중 하나여야 한다. 예: `-N 2 --gpus=8`이면 노드마다 4장.
    - GPU가 8장보다 적은 노드도 있다. 노드별 GPU 수는 `sq`로 확인한다.
- **CPU 전용 잡은 CPU 수를 필요한 만큼 자유롭게 지정**해도 된다. 파티션은 적지 않는다. 다만 CPU 전용 잡으로 **GPU 노드를 통째로 차지할 수는 없다**.
  `--exclusive`나 `--mem=0`을 적으면 제출이 거부된다.
- **한 잡에는 GPU 타입 하나만** 요청한다. 여러 타입을 섞으면 제출이 거부된다. 타입마다 따로 제출한다.
- **`--qos`를 생략하면 기본 QoS로 제출된다.** 기본 QoS 잡은 남는 자원을 쓸 수 있는 대신, 팀 QoS 잡이 그 자원을 가져갈 수 있다(**선점**, preemption). 선점된 잡은 큐로 돌아가 **처음부터** 다시 실행된다. 긴 잡은 반드시 체크포인트를 남긴다. -> [선점 설명](../reference/slurm.md#선점)

GPU를 점유하는 세션의 규칙:

> **GPU 점유의 뜻**
> 인터랙티브 터미널, Jupyter Notebook, **요청을 기다리는 추론 서버**처럼 **GPU를 언제 쓸지 사용자가 직접 정하는 모든 상황**을 말한다.
> 단, **데이터 처리가 끝나면 스스로 자원을 반납하는 자동화 잡**은 여기에 해당하지 않는다.

`srun`, `salloc`으로 여는 GPU 세션은 팀 QoS(`--qos=<팀 QoS>`)로만 시작할 수 있다. 팀 QoS 없이 제출하면 `qos`로 내 QoS를 확인하라는 안내와 함께 거부된다.

```bash
# GPU를 점유하는 인터랙티브 셸 (팀 QoS는 본인 것으로. `qos` 로 확인)
srun --qos=<팀 QoS> --time=04:00:00 --gres=gpu:<GPU 타입>:1 --pty bash -i
```

클러스터가 GPU 사용률을 상시 감시한다.
Slurm 잡이 할당받은 GPU를 **2시간 넘게 쓰지 않으면** 알린다. 할당받은 GPU를 **6시간** 동안 쓰지 않은 잡은 자동으로 취소되고, 취소 **1시간 전**에 미리 알린다.
여기서 할당받은 GPU를 쓰지 않는다는 것은 그 잡이 할당받은 GPU가 **모두** 그 시간 내내 쉬었다는 뜻이다.
그중 한 장이라도 쓰이면 클러스터는 시간을 처음부터 다시 센다.

## 요청을 몰아서 보내지 않기

- 짧은 시간에 많은 요청을 보내지 않는다. SSH 접속이나 `squeue`, `sq`, `sacct` 같은 스케줄러 조회를 빠르게 반복하면(예: `watch -n 1`)
  스케줄러와 네트워크가 느려져 모든 사람이 영향을 받는다.
- 잡이 끝나기를 기다릴 때는 반복 조회 대신 **`sbatch --wait`**, `srun`(끝날 때까지 기다림), 또는 `--dependency`를 쓴다.
- 상태를 계속 지켜봐야 하면 직접 반복하지 않고 `sq -i <초>`를 쓴다. `sq`는 너무 짧은 간격을 받지 않고, Slurm이 답하지 않으면
  스스로 간격을 늘린다.
- 클러스터 명령 가운데 `--json`이 있는 명령(`qos`, `sq`, `usage`, 하위 명령 포함)의 결과는
  화면 출력을 해석하지 않고 `--json`으로 읽는다. Slurm이나 Prometheus가 답하지 않아 실패한 명령은 반복해서 다시 실행하지 않는다.
  출력 형식과 종료 코드는 각 명령의 `-h`(예: `usage -h`)에 있다.

## 장시간 세션

에이전트를 오래 실행할 때는 아래를 반드시 지킨다.

- 직접 띄운 백그라운드 프로세스, 끝나지 않은 하위 프로세스, 좀비 프로세스를 남기지 않는다. 다 쓴 것은 정리한다.
- 메모리, 열린 파일, 임시 파일이 계속 늘어나는 누수가 없는지 살핀다.
- 세션을 끝낼 때 그 세션이 띄운 프로세스를 정리하고, 그 세션이 낸 잡 가운데 더 실행할 필요가 없는 잡(열어 둔 `salloc` 할당 등)을
  취소한다. 사용자가 실행하라고 한 잡은 그대로 둔다.

## 로그인 노드와 공유 스토리지

공유 스토리지는 모두가 함께 쓴다. 한 사람의 I/O가 모든 사람의 잡을 느리게 할 수 있으므로, 데이터를 알맞은 곳에 두고 I/O를 줄인다.

**1. 성격에 맞는 데이터 위치**

| 공간 | 성격 | 용도 |
|---|---|---|
| `/home` | 용량이 크고 오래 보관하는 공간. HDD RAID라서 큰 파일을 처음부터 순서대로 읽고 쓰면 빠르다. 작은 파일을 여기저기 읽고 쓰면 매우 느리다 | 코드, 결과, **묶음 파일로 보관하는** 데이터셋 |
| `/scratch` | 진행 중인 실험이 자주 읽고 쓰는 작업본을 두는 NVMe RAID. 작은 파일, 무작위 접근, 체크포인트에 강하다. 60일 동안 아무도 읽거나 쓰지 않은 파일은 정리된다 | 진행 중인 실험의 작업본 (임시) |
| 잡의 `/tmp` | 잡이 실행 중인 노드의 로컬 디스크에 잡마다 따로 생기고, 잡이 끝나면 지워진다 | 풀어 놓은 실행 환경, 압축을 푼 데이터셋, 한 잡의 임시 파일 |

**2. I/O 줄이기**

- 작은 파일 수만 개는 **묶음**(tar, WebDataset 샤드, LMDB, HDF5, Parquet)으로 만들어 순서대로 읽는다.
  압축이 필요하면 gzip 대신 zstd(`tar -I "zstd -T$(nproc)"`)를 쓴다. 압축하고 푸는 속도가 훨씬 빠르다.
- Python 환경은 미리 파일 하나로 묶어 `/home`에 두고, 잡이 시작할 때 그 잡의 `/tmp`에 푼다.
  묶는 방법은 lockfile로 만든 uv 가상환경을 묶거나 conda-pack을 쓰는 것이다. 컨테이너 이미지(Enroot, Podman)도 파일 하나라서 효과가 같다.
  ([잡 레시피](../guide/job-recipes.md#실행-환경-묶어서-쓰기))
- 잡 안에서는 클러스터가 패키지 캐시(`UV_CACHE_DIR`, `PIP_CACHE_DIR`)를 그 잡의 `/tmp`로 정해 둔다. 공유 스토리지로 바꾸지 않는다.
  필요한 모델이 공용 모델 캐시(`SHARED_HF_HUB_CACHE`)에 있으면 각자 내려받지 않고 그 캐시에서 읽는다.
  ([환경 변수](../guide/storage.md#환경-변수))
- 체크포인트는 **크게, 드물게** `/scratch`에 쓰고, 남길 최종본은 `/home`으로 옮긴다. 학습 스텝마다 작은 로그를 공유 스토리지에 쓰지 않는다.

**3. 무거운 파일 작업 삼가기**

- 큰 디렉터리 트리 전체에 `du`나 `find`를 실행하지 않는다. 큰 `rsync`나 `tar`도 로그인 노드에서 하지 않는다.
  내 사용량은 `usage disk`로(파일시스템별 사용량과 한도, 정리하면 좋을 폴더), 전체는 디스크 리포트로 확인한다.
````
